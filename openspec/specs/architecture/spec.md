# Architecture Specification

## Purpose

SpecHarbor follows Hexagonal Architecture, SOLID, Clean Code, and pragmatic design patterns to keep the application core independent from CLI concerns, file system operations, templates, AI providers, coding agents, workflow tools, and external APIs.

The project must be easy to extend without modifying stable use cases.

## Architectural Layers

### Domain

Domain code contains pure business concepts and value objects.

Location:

```text
internal/core/domain
```

Rules:

- Must not depend on adapters.
- Must not access file system, network, terminal, environment variables, or external APIs.
- Must not import infrastructure packages.
- Must represent SpecHarbor concepts such as changes, specs, agents, providers, generation modes, authoring modes, validation findings, and project context.

### Ports

Ports define interfaces required by use cases.

Location:

```text
internal/core/ports
```

Examples:

- `FileSystem`
- `ProjectScanner`
- `SpecAuthor`
- `SpecGenerator`
- `PromptGenerator`
- `SpecValidator`
- `AIProvider`
- `AgentPromptGenerator`
- `WorkflowDispatcher`
- `TemplateRenderer`
- `ConfigRepository`

Rules:

- Interfaces must be small.
- Interfaces must be owned by the consuming layer.
- Use cases must depend on ports, never concrete adapters.

### Use Cases

Use cases contain application orchestration.

Location:

```text
internal/core/usecase
```

Rules:

- May depend on domain and ports.
- Must not depend on concrete adapters.
- Must not contain CLI-specific formatting.
- Must not call `os`, HTTP clients, provider SDKs, template engines, or terminal IO directly.
- Must return structured results and errors.

### Adapters

Adapters contain concrete implementations of ports.

Location:

```text
internal/adapters
```

Rules:

- Adapters may depend on core ports and domain.
- Adapters must not define business rules.
- Provider-specific payloads, authentication, errors, rate limits, retries, and response mapping must stay inside adapters.

### Platform

Platform packages contain cross-cutting technical utilities.

Location:

```text
internal/platform
```

Rules:

- Keep platform code minimal.
- Avoid global mutable state.
- Do not hide business rules in platform packages.

## Dependency Rule

Dependencies must always point inward:

```text
cmd -> adapters -> core/usecase -> core/ports + core/domain
```

Forbidden dependencies:

```text
core -> adapters
core -> cmd
usecase -> concrete provider
usecase -> os package directly
usecase -> HTTP client directly
usecase -> terminal directly
```

## SOLID Rules

### Single Responsibility Principle

Each package, struct, and function must have one clear reason to change.

### Open/Closed Principle

The project must be open for extension and closed for modification.

Adding a new generation mode, spec authoring mode, AI provider, coding agent, workflow connector, scanner, validator, or prompt generator must be done by adding a new implementation and registering it through a registry/factory.

Use cases must not grow large `switch` statements for every new provider or agent.

### Liskov Substitution Principle

All implementations of a port must be replaceable without breaking use cases.

### Interface Segregation Principle

Prefer small interfaces.

Avoid large interfaces that mix spec generation, prompt generation, implementation review, and workflow dispatching.

Prefer smaller contracts such as:

- `SpecDraftProvider`
- `PromptDraftProvider`
- `ImplementationReviewer`
- `WorkflowDispatcher`

### Dependency Inversion Principle

Use cases depend on abstractions, not concrete implementations.

Concrete implementations belong to adapters and are injected into use cases from the application bootstrap.

## Spec Authoring Strategy

SpecHarbor must not assume that specs are always generated by direct AI provider API calls.

Spec generation must support multiple authoring strategies:

- Blank authoring
- Guided authoring
- Template authoring
- AI-provider authoring
- Agent-assisted authoring
- Hybrid authoring

### Blank Authoring

Creates the minimal OpenSpec structure so users can write everything manually.

### Guided Authoring

Asks questions and generates OpenSpec files from user answers.

### Template Authoring

Uses built-in or custom templates.

Templates are accelerators, not mandatory workflows.

### AI-provider Authoring

Uses a configured AI provider API or local model to generate spec drafts.

Examples:

- OpenAI-compatible APIs
- Anthropic
- Gemini
- Ollama
- Azure OpenAI
- OpenRouter
- Mistral
- Groq
- LM Studio
- LocalAI

### Agent-assisted Authoring

Used when a company provides access to tools such as Devin, Codex, Claude Code, Cursor, GitHub Copilot, Windsurf, Aider, Roo Code, or similar coding agents, but does not provide direct provider API keys.

In this mode, SpecHarbor generates an authoring package and an agent-specific prompt so the external agent can create the OpenSpec files.

The agent-assisted mode must not require API keys.

Expected output:

```text
openspec/changes/<change-id>/
  proposal.md
  design.md
  tasks.md
  acceptance-criteria.md
  risks.md
```

### Hybrid Authoring

Combines project scanning, user answers, templates, AI provider output, and/or agent-assisted prompts.

## AI, Agent, and Workflow Integration

SpecHarbor separates AI model providers from coding agent targets and workflow connectors.

### AI Model Providers

AI model providers generate structured content such as specs, prompts, reviews, and summaries.

Examples:

- OpenAI
- Anthropic
- Gemini
- Ollama
- Azure OpenAI
- OpenRouter
- Mistral

They must implement small provider ports such as `SpecDraftProvider`.

Provider-specific details must not leak into use cases.

### Agent Targets

Agent targets are tools that consume specs or prompts to implement or author changes.

Examples:

- Codex
- Claude Code
- Cursor
- Devin
- GitHub Copilot
- Gemini CLI
- Roo Code
- Windsurf
- Aider
- Generic Agent

They must implement prompt generation strategies through `AgentPromptGenerator`.

### Workflow Connectors

Workflow connectors integrate SpecHarbor with external execution or project management tools.

Examples:

- GitHub
- GitLab
- Jira
- Linear
- Devin
- Slack
- CI systems

They must implement dispatcher ports and must not leak external SDK details into use cases.

## Required Design Patterns

### Strategy Pattern

Use for:

- spec authoring modes
- generation modes
- AI providers
- agent prompt generators
- workflow dispatchers
- validators when applicable

### Factory / Registry Pattern

Use to resolve:

- spec author by authoring mode
- AI provider by provider name
- prompt generator by agent target
- workflow connector by target
- validator chains
- scanners

### Adapter Pattern

Use for:

- file system
- terminal IO
- AI APIs
- coding agent tools
- template rendering
- Git/GitHub/GitLab integrations
- config storage

### Chain of Responsibility

Use for:

- spec validation pipeline
- architecture rule validation
- project scanning pipeline when useful

### Command Pattern

Use for:

- CLI command execution

## Testing Rules

- Domain must be tested without mocks when possible.
- Use cases must be tested with mocked ports.
- Adapters must have focused tests for integration behavior.
- CLI commands must be tested through command input/output.
- Validators must be tested with valid and invalid specs.
- Avoid testing implementation details unless required by behavior.

## Agent Rules

Any coding agent must:

- read `openspec/project.md`;
- read this architecture spec;
- read the active change under `openspec/changes/<change-id>`;
- preserve dependency boundaries;
- avoid unrelated refactors;
- update `tasks.md` after implementation;
- run tests or explain why tests could not be run.

## Enforcement

Architecture rules should be enforced gradually through:

- OpenSpec validation;
- package boundaries;
- tests;
- CI checks;
- future architecture validators inside SpecHarbor itself.
